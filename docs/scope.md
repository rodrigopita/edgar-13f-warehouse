# Project 2: SEC EDGAR 13F Warehouse

## Goal

Build a Snowflake warehouse answering:

> **Who holds what, and how did institutional positions change quarter-over-quarter?**

This is the flagship project because it combines a realistic domain, semi-structured data, incremental ingestion, warehouse modeling and difficult data-quality rules.

**Snowflake timing constraint:** activate the Snowflake trial only when Steam is complete and EDGAR is ready to enter its Snowflake phase. The trial ends after 30 days **or** when the free credit balance is exhausted, whichever comes first, so the implementation must fit inside that window and careless compute can end it early. From day one: X-Small warehouse, aggressive auto-suspend, and a resource monitor capping credit consumption.

## Historical vs incremental ingestion

### Historical backfill: TSV only

**Do not build a historical XML parser.**

The SEC publishes first-party 13F datasets that are extracted from the XML-based portions of EDGAR submissions and provided in flattened form. They already cover the historical data needed for the warehouse.

Reasoning:

- the TSV data is an official SEC representation of the structured filing data
- historical XML parsing adds large amounts of edge-case work with little additional portfolio signal
- the project needs historical volume, not an archaeological reconstruction of every filing
- time is better spent on amendment resolution, tests, incremental processing and warehouse design

The project therefore treats the TSV datasets as the **correct historical ingestion path**, not a shortcut or fallback.

### Incremental ingestion: XML

Use raw 13F XML for newly discovered filings.

This still proves the ability to:

- retrieve and store semi-structured source data
- parse XML into typed records
- handle malformed/unexpected structures
- process amendments
- incrementally update the warehouse

No time should be spent making the XML path reproduce the entire historical dataset.

## Modeling

Use a normalized core layer where it solves a real problem, then build dimensional marts. The core exists to resolve amendments and supersedence once, producing a canonical holdings state that multiple downstream marts can consume. Revised 2026-10-19: cp3 builds the filing, the lineage with its supersedence state, holdings and canonical holdings; filer, security and period are built in cp4 with the marts that read them.

Core:

- `filer`
- `security`
- `filing`
- `period`
- canonical amendment / supersedence state
- `holding`

Marts:

- portfolio evolution
- new positions / exits
- concentration metrics
- institutional portfolio overlap

## Key engineering problem: amendments

13F amendments are the project's main data-correctness challenge.

The pipeline must distinguish original filings from amendments and resolve the canonical state before downstream marts consume it.

This is a stronger engineering showcase than simply demonstrating that XML can be parsed.

## Data quality

Examples:

- holding quantity and value constraints
- unique filing lineage
- amendment supersedence tests
- duplicate detection
- unit normalization across historical periods
- reconciliation between raw and canonical record counts

## Observability

Track:

- filings discovered vs loaded
- ingestion failures
- XML parsing failures
- amendment resolution failures
- duplicate/superseded filings
- raw-to-modeled row counts
- pipeline freshness

## Domain constraints

- respect EDGAR's published maximum of 10 requests/second and declare a meaningful `User-Agent` containing contact information
- do not scrape proprietary CUSIP→ticker mappings
- make identifier limitations explicit in the README
- frame analytics around filing dates and reporting periods, not real-time positions

## Snowflake features to use deliberately

Use platform features because they solve a problem:

- **VARIANT** for raw semi-structured records
- **Snowpipe** for incremental ingestion
- **Streams & Tasks** for incremental state changes
- **dbt incremental models/snapshots** where appropriate
- **Time Travel** for recovery/debugging
- **Zero-copy cloning** for a development environment
- **RBAC** to separate ingestion/transformation/analytics responsibilities

Do not add features merely to increase the technology checklist.

## Checkpoints

1. **Extraction proven, trial untouched** (`cp1-extraction`). Everything runs locally so the 30-day clock is not burning. The index walker discovers filings and downloads XML at polite rates with the declared `User-Agent`; the parser produces typed records; the TSV historical datasets are downloaded and profiled with row counts written down. Done when the parser handles representative real filings plus deliberately crafted malformed fixtures. Fixtures are built, not hunted: real malformed filings will appear during operation anyway.

2. **Snowflake ingests without hands** (`cp2-snowpipe`). Trial activated; resource monitor set the same hour. Terraform applies the stage, pipe and notification wiring; the TSV backfill is loaded. Done when a new XML file dropped in S3 appears in the VARIANT raw table with no manual step, and backfill row counts reconcile against the checkpoint 1 profile. Revised 2026-10-13: with the parser in Python, the walk run that lands a filing's XML also parses it, and the JSON-lines file it writes to S3 is what Snowpipe loads with no manual step.

3. **Canonical holdings are correct** (`cp3-canonical`). The intellectual center of the project. Core layer built, supersedence state working, restatement-versus-addition logic tested. Done when a hand-picked filer with a known messy amendment history shows correct canonical holdings, and the supersedence and lineage dbt tests are green.

4. **Warehouse answers questions** (`cp4-marts`). QoQ marts live: portfolio evolution, entries and exits, concentration, overlap. Done when "what did filer X buy and sell last quarter" is one query, and the answer matches a manual spot-check against the actual filing on EDGAR's website. The external oracle matters: here is what the source says, here is what my system says.

5. **Platform is operable and recoverable** (`cp5-operability`). The purpose is operability, not feature box-checking; the features are the evidence. RBAC as operational separation, zero-copy clone as the development workflow, one recorded Time Travel recovery, audit tables populated, README done. Done when the failure demo exists as a script or recording and the README answers all eight questions.

## Stretch ideas

Alternative identifier enrichment, additional marts, or deeper Snowflake experiments may be added only after the core warehouse is correct, tested and documented.

## What this project proves

> I can design a warehouse around messy public data, separate historical backfill from operational incremental ingestion, resolve difficult data-correctness problems, and use Snowflake/dbt features for clear architectural reasons.

Revised 2026-10-13: a filing that fails to parse writes no file and is recorded in the run's audit record in S3; a `reconcile` gap is recorded there too, but its file loads, as the layout bullet below says. - **One JSON-lines file per filing, `parsed/edgar/filings/filed=YYYY-MM-DD/<accession>.jsonl`, loaded into `RAW.PARSED_FILINGS`.** The cover page is the first line and each holding follows, each wrapped as `{record_type, accession, source_key, record}`, so a filing reaches the warehouse whole or not at all and every row names the XML it came from. Keys and bytes are deterministic, like the raw XML: Snowpipe ignores a path it processed in the last 14 days even if the file changed, and the walk re-lands only the last 7 days, so a rerun never loads twice. A filing that fails to parse writes no file; the failure and any `reconcile` gap go into the run's audit record. Load time is the table's row timestamp, because the pipe docs say a `CURRENT_TIMESTAMP` default records when the load compiles, not when it commits. Decided 2026-10-11.
- **The data set zips land as fetched under `raw/sec/datasets/`; their tables are re-compressed one file per table and zip under `extracted/sec/datasets/table=<TABLE>/<data set>.tsv.gz` and loaded by COPY into seven text tables, `RAW.DATASET_<TABLE>`.** Snowflake's file formats read gzip and not zip, so the zip stays the raw record and the gzip copy is what loads. The gzip header carries no timestamp, so a rerun writes the same bytes, and bulk COPY skips a file it loaded in the last 64 days. Each table has one header in all 54 zips, so each raw table is one fixed column list, kept as text with the data sets' own names. A scan of all 125.9 million rows on 2026-10-11 found no column-count mismatch, no CRLF and no invalid UTF-8, but 4,100 rows with a backslash and 7,907 with a double quote, so the TSV format sets `ESCAPE_UNENCLOSED_FIELD = NONE` (the default backslash would read them as escapes, and a trailing one joins two rows) and leaves `FIELD_OPTIONALLY_ENCLOSED_BY` at its default `NONE`. The largest file, `INFOTABLE` of 01jun2026-31aug2026, is 397 MB uncompressed, inside Snowflake's guidance of 100 to 250 MB compressed per file. Decided 2026-10-11.

The key expires with the trial on 2026-11-08. `include/sql/05_airflow_identity.sql`.

- **Filing order within a lineage is filing date, then accession number.** The amendment number on the cover page is assigned by the filer, so it is recorded and not trusted for order, and the SEC's 13F FAQ (58b) says only that the filer numbers amendments to tell them apart. The data sets carry the filing date of every submission, and the accession number's last segment is the filing agent's sequence within the year. Two filings of one lineage on one date, which Brookfield's two restatements of November 2018 avoid by a day, get a data-quality row. Decided 2026-10-15; the terms are in `CONTEXT.md`. Revised 2026-10-16: the SEC's Accessing EDGAR Data page defines the first ten digits as the CIK of the entity submitting the filing and the last six as "a sequential count of submitted filings from that CIK", so filings of one date under one prefix are in submission order, and only filings of one date from different submitters get a data-quality row. A local profile of the 54 data sets found 1,120 lineages where accession order within a date picks the effective restatement, 22 of them across submitters. Revised 2026-10-17: within one date the cover's amendment number orders filings before the accession does, an original first since it carries none. The SEC's FAQ 58c files a correction with additions as two amendments, the restatement first and the addition second; of the 49 additions a restatement of the same date superseded, the 27 numbered after it lost securities it did not list, and the 16 numbered before it were listed whole in it. The change reorders 88 filings in 43 lineages, each with a data-quality row, and alters the contributing filings of 36 of those lineages, 27 of them gaining their addition. Advisors Asset Management, 2019-03-31, is the case in the unit tests.
- **A restatement supersedes every holdings report before it in the lineage, an addition supersedes nothing, and canonical holdings are the holdings of the contributing filings: the latest restatement, or the original when none exists, plus every addition after it.** FAQ 58b: an amendment that corrects an error must resubmit the entire filing as corrected. FAQ 58c: an amendment adding new holdings lists only the securities being added and supplements the original. Check: Brookfield Corp /ON/, period 2018-06-30, resolves to the 191 holdings of the restatement of 2018-11-15 plus the one holding added on 2018-12-14, with the original and the two-row restatement of 2018-11-14 superseded. Decided 2026-10-15. Revised 2026-10-16: 228 lineages in the data sets have an addition filed before a later restatement, which this rule supersedes; a data-quality row records each superseded addition whose securities the restatement does not list, so the rule is checked against the holdings. Revised 2026-10-20: an addition that repeats nine tenths or more of the securities of the filing it amends, the latest original or restatement before it as typed, counts as a restatement and gets a data-quality row; `addition_coverage` holds each addition's compared filing and coverage. A profile on 2026-10-19 found 998 contributing additions that did, $24.0 trillion counted twice, against 3,734 that repeat under a tenth and 160 between; 1,648 of the 3,734 tick the cover's box for confidential treatment denied or expired, and 1 of the 160. A separate pass over the 54 zips counts 1,040 of the 5,121 additions in the data sets at or over the line. The filings on sec.gov show why: Morgan Stanley's two additions for 2024-03-31 each resubmit the original's 46,942 holdings with one holding more and write that "The Firm is restating its 13F", and Deutsche Bank's for 2018-06-30, filed 2020-04-21, is a corrected list of 21,882 holdings. Comparing with the roles as typed keeps the rule from depending on itself, and Morgan Stanley's second addition, compared with the original as the first is, becomes the effective filing.
- **A filing the rules cannot read as filed counts as a restatement and gets a data-quality row: an untyped amendment, of which the data sets hold 55, and a second original for the same period. An addition that repeats a security already in effect keeps both holdings, flagged. A lineage that starts with an amendment stands on the filings present, flagged.** The FAQ's procedure resubmits the whole filing unless the cover page's new-holdings box is checked, so an unchecked box reads as the base case rather than a guess from entry counts. Merging a repeated security would invent a value the filer never reported, and one security may appear in several holdings of one filing by discretion or other manager. The data sets begin with filings of April 2013, so lineages for earlier periods start mid-chain. Decided 2026-10-15. Revised 2026-10-16: the count of untyped amendments was 14 until the lineage profile, which found 53 to holdings reports in 52 lineages and 2 to notices; the cp1 profile had subtracted the typed filings of every submission type from the amendments. The same profile found 421 lineages that start with an amendment: 262 for periods before 2013, 50 in the first data set, 109 for later periods whose original is absent. Revised 2026-10-19: under the filing order of 2026-10-17 an original comes first among the filings of its date, so 413 lineages start with an amendment. Revised 2026-10-20: a holding of an addition identical to one already in effect, in security, put or call, amount, amount type, discretion and other managers, is a copied holding: it leaves the canonical holdings and its filing gets a data-quality row. Dropping a copy keeps the value the filer reported, once, so the reason against merging holds. Janus Henderson's addition for 2022-09-30 repeats 86 percent of its original's securities, under the restatement line, and 5,635 of its 5,642 holdings are copies; the 7 left repeat securities at other amounts, about 0.17 percent of the filer's value, and stay. Prudential's for 2020-09-30 adds the book of Pruco Securities, an other manager the original left out: 1,148 of 2,239 securities repeat and no holding is a copy, so all 1,368 stay.
- **Notices join the lineage and never supersede holdings; a notice amendment amends a notice. The canonical state is the current one, and an as-known-on-date view is a cp4 mart if one is wanted.** A notice says another manager reports the holdings and carries none, so it changes nothing about what is in effect. Consequence: the two 13F-NT filings with a summary page that the parser refused on 2026-10-14 (`0001758171-26-000005`, `0001510483-26-000007`) are notices with extra data, so the parser's rule that a notice has no summary page is relaxed in cp3 and they load. Decided 2026-10-15. Revised 2026-10-21: eleven notices in the data sets list holdings anyway, ten typed 13F-NT and one 13F-NT/A, all filed before 2022, 549 holdings worth $1.72 billion. They stay out of canonical holdings, since the filer says another manager reports them; each gets a data-quality row, `notice_with_holdings`, and `row_counts` counts their holdings apart. Its balance test found them, and a separate pass over the 54 zips finds the same 11 filings and 549 rows, six of them from one submitter, filed from 2013 to 2014, each listing two holdings worth $141,966 thousand.
- **A lineage is one filer's filings for one period of report, the period EDGAR records with the submission. Where the submission type and the cover disagree, the submission type decides whether a filing is an original, an amendment or a notice, the cover's amendment type decides restatement or addition, and the disagreement gets a data-quality row.** The XML parser reads the period from the same header field the data sets carry as `PERIODOFREPORT`; the cover's own period differs in 5 filings, one of them 1900-01-01 and one the filing date. The cover's amendment box disagrees with the submission type in 93 filings: 41 typed 13F-HR tick it and name an amendment type, and 52 are untyped amendments whose box is blank or N. Separately, 11 typed 13F-NT call themselves holdings or combination reports and have no summary page; their report type disagrees with the submission type and gets its own data-quality row. Corrected 2026-10-17: the first version counted the 11 notices inside the 93. Reading the cover's amendment type first instead changes the contributing filings of none of the 307,613 holdings-report lineages, so the rule follows EDGAR's record and keeps the cover as evidence. Decided 2026-10-16.
- **Staging is eleven views in `CORE`, one per raw data set table and four over the XML envelope, with the data set conventions written once as macros.** A view costs nothing until it is read and the core tables materialize from them, so the typing happens in one named place: blank to null, `DD-MON-YYYY` to date, Y and N to boolean, with VALUE and TABLEVALUETOTAL kept as filed. The two paths share column names, so the core layer sets them side by side, and both keep their own row identity, `INFOTABLE_SK` and the XML `row_index`, for lineage. The XML envelope keeps one file version per filing, the one written last, because Snowpipe loads a path again after 14 days. Checks: three dbt unit tests, for values as filed and the other-manager field, the flags and dates, and the dedupe; a pytest that finds every raw column name from `sec_backfill` in the staging SQL. Decided 2026-10-16. Revised 2026-10-17: values stay as filed in staging and the core reads each filing's unit, so the holdings and summary views no longer join the submission; the first version multiplied by the filing-date rule here.
- **The supersedence state is one model, `lineage_filings`: every filing with its position in its lineage, its role, and whether it is superseded or contributing. Nine dbt unit tests pin the rules, and data tests check the state of every lineage.** The model is plain SQL, so its unit tests ran in a local DuckDB copy outside the repository before the Snowflake run, one rule at a time, each red before green. Four rules already held when their tests arrived; breaking the model four ways, by reversing the accession order, by never superseding additions, by reading an untyped amendment as an addition and by keying lineages on the filer alone, failed exactly the matching test each time. The data tests: one filing per lineage position, every filing in a lineage, exactly one effective filing in a lineage with an original or a restatement, no superseded filing contributing, notices doing neither, every addition after the effective filing contributing, and Brookfield's lineage for 2018-06-30 as filed. Decided 2026-10-16. ## Source facts

Checked against sec.gov on 2026-09-23 with the project User-Agent. Re-check before relying on them in a later checkpoint.

- **Dataset zips are cut by filing date, not reporting period.** 54 files, windows from 2013-04-01 to 2026-08-31, the SEC page labels them July 2013 to August 2026, 3.05 GB compressed. Older names look like `2013q2_form13f.zip`, newer ones like `01jun2026-31aug2026_form13f.zip`. A zip holds filings submitted in its window, cutoff 5:30 PM Eastern on the quarter's last business day. One period spans many zips through late filers and amendments, so cp2 reconciles per zip and the period dimension comes from PERIODOFREPORT. A COVERPAGE row in the June to August 2026 zip reports period 30-SEP-2001.
- **VALUE changed units on 2023-01-03.** From the SEC readme inside each zip: "Starting on January 3, 2023, market value is reported rounded to the nearest dollar. Previously, market value was reported in thousands." This is the unit normalization rule. The boundary is verified during cp1 profiling. Revised 2026-10-17: the rule is the default, not the reading. A filing's median value per share as filed shows its unit, and by that test the filing-date rule misreads 13,499 of about 318,000 holdings filings in the data sets; see the value-unit decision.
- **INFOTABLE carries a nullable FIGI next to CUSIP.** Filing 0001535452-26-000006 populated it on all 393 rows, 0001214659-26-011877 on none. FIGI is an open identifier, so enrichment through OpenFIGI is the strech path that respects the no-CUSIP-scraping rule. Before 2023, CUSIP is the only key.
- **The info table XML has no fixed name.** Every filing folder has `primary_doc.xml` plus one info table file named by the filer, `infotable.xml` in one filing and `AP2ReportQ22026.xml` in another. The downloader reads the folder's `index.json` instead of guessing.
- **Observed rate.** 20 sequential requests at 7.9 per second, all 200, no 429 or 403. The policy page reads "Current max request rate: 10 requests/second."
